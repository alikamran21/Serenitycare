The Problem: Vulnerability in Healthcare DBs

The Flaw of Traditional DBMS

Traditional database security operates on a rigid, binary "Access/Deny" paradigm.

Once a threat actor bypasses the perimeter (via SQL injection, compromised credentials, etc.), the system implicitly trusts the authenticated session, giving free rein to scrape or destroy data.

Passive security simply blocks known attacks, which inadvertently alerts the hacker to adapt their tactics.

Why Medical Data (PHI)?

Unlike financial data (credit cards), which can be frozen or reissued, a patient's psychiatric history, therapy notes, and SSNs are immutable.

  • High value for ransomware and blackmail.
  • Irreversible damage upon exfiltration.
  • Requires defense beyond just "blocking."

Our Solution: Active Defense & Deception

Phantasm-DB: The Deception Engine

Instead of passively blocking malicious requests, we built an autonomous "Active Defense" middleware. It intercepts attacks and silently traps the hacker in a "Shadow Schema"—a structurally identical but entirely synthetic honeypot.

1. Deep Packet Inspection

Heuristic functions scan payloads against a Detection_Policies matrix (e.g., regex for SQLi) to flag malicious sessions instantly.

2. The Honeypot Gate

Context-switching short-circuits flagged requests. The attacker gets HTTP 200 (OK) but interacts with procedurally generated decoy objects.

3. Forensic Archiving

A logging mechanism writes the attacker's raw SQL payloads, network fingerprints, and behavioral metrics to an immutable relational ledger.

Applying Database Normalization

We structured our 10-table schema to minimize redundancy, prevent data anomalies, and optimize query speed during real-time threat analysis.

First Normal Form (1NF)

Rule: Atomic values, no repeating groups.

Implementation: The Detection_Policies table stores single regex patterns per row rather than an array of patterns, allowing the heuristic engine to query specific threat signatures instantly.

Second Normal Form (2NF)

Rule: 1NF + No partial dependencies on composite keys.

Implementation: In Real_Time_Alerts, attributes like severity depend entirely on the composite primary key, not just a part of it, ensuring alert integrity.

Third Normal Form (3NF)

Rule: 2NF + No transitive dependencies.

Implementation: The Forensic_Ledger links to Global_Identities via foreign key. We do not duplicate the ip_address in the ledger; it is retrieved via relational join, avoiding update anomalies if an IP changes.

Database Triggers & Throttling

We utilized SQL Triggers as a "Tripwire" mechanism. If an attacker touches a Honey_Token (a fake record), the trigger automatically fires a stored procedure to insert an alert and implement query throttling (e.g., pg_sleep()) to slow down data dumping.

Simulation Mechanics & System Security

1. The Attack Vector

An adversary attempts a SQL injection on the authentication endpoint: DOC-001' OR 1=1 --.

2. The Detection Phase

The heuristic engine identifies the Boolean inference. The attacker’s IP is logged, and the is_flagged parameter is tripped.

3. The Deception Phase

The system synthesizes a successful authentication response. The attacker drops into the dashboard, which is now populated entirely by the Shadow_Manifest.

4. The Resolution

Attacker scrapes fake data. Real data remains cryptographically secure. 0% PHI Compromised.

Admin SIEM Dashboard

The simulation features a hidden Security Operations Center (SOC) dashboard that allows admins to view the Live Ledger, track threat actors, and visualize the intercepted queries in real-time.
